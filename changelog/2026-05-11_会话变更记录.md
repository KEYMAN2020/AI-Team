## 变更清单

### 一、按角色独立配置超时（Per-Role Timeouts）

**目标**: PM 规划 30s 够用，Frontend 写代码可能需要 300s+，不再一刀切。

**涉及文件**:
- `references/model_adapter.py` — 新增超时配置
- `references/runner.py` — 读取并传入超时参数

**关键改动**:
1. `model_adapter.py` 新增 `DEFAULT_TIMEOUT = 180` 全局默认值
2. `ROLE_CONFIGS` 中每个角色新增 `"timeout"` 字段：
   - PM=120s, Product=90s, UX=90s, Architect=120s
   - DBA=300s, Frontend=600s, Backend=600s
   - Reviewer=120s, DevOps=300s, Debug=600s, Tester=300s
3. 新增 `get_role_timeout(role, provider)` 函数
4. `runner.py` 的 `run_dag()` 调用 `get_role_timeout()` 传给 `run_agent()`

### 二、Token 用量追踪

**目标**: 每次跑完任务能看到每个角色花了多少 token、预估费用。

**涉及文件**:
- `references/model_adapter.py` — 核心改动

**关键改动**:
1. 新增线程安全的 `_token_usage` 列表 + `_usage_lock`
2. 新增 `PROVIDER_COST_PER_1K` 定价字典（deepseek/claude/openai/gemini）
3. 新增函数：`record_usage()` / `get_token_usage()` / `reset_token_usage()` / `compute_usage_summary()`
4. 所有 5 个 `_call_*` 函数（对应 5 个 LLM 提供商）提取 API 响应的 usage 字段并调用 `record_usage()`
5. `runner.py` 的 `run_project()` 结束时调用 `compute_usage_summary()` 打印摘要

**输出示例**:
```
=== Token 用量统计 ===
按角色:
  pm:        input=1,200  output=850  费用=$0.0092
  backend:   input=4,500  output=2,100 费用=$0.0258
  ...
按提供商:
  claude:    input=8,400  output=3,800 费用=$0.0822
总计: input=12,800  output=5,600  总费用=$0.1254
```

### 三、PM DAG 预览（人工确认）

**目标**: PM 规划完 DAG 后先展示给用户看，确认后再执行，避免盲目运行。

**涉及文件**:
- `references/runner.py` — 预览 + 双阶段审批逻辑
- `server.py` — 新增 `POST /approve-dag` 端点

**关键改动**:
1. `runner.py` 新增 `_format_dag_preview(dag)` — 将 DAG 格式化为可读文本
2. `runner.py` 新增 `_request_dag_approval(dag)` — 双阶段审批：
   - HTTP 模式：Phase 1 等确认（无超时），Phase 2 等决策（3600s 超时）
   - CLI 模式：单次 `input()` 确认
3. `run_project()` 在 DAG 提取后、执行前插入预览步骤
4. `server.py` 新增 `POST /approve-dag` 路由

**API 用法**:
```bash
# Phase 1: 确认收到
curl -X POST http://localhost:8123/approve-dag \
  -H "Content-Type: application/json" \
  -d '{"status": "reviewing"}'

# Phase 2: 做出决策
curl -X POST http://localhost:8123/approve-dag \
  -H "Content-Type: application/json" \
  -d '{"approved": true}'
```

### 四、QA→DBG→QA 循环（Bug 自动修复迭代）

**目标**: Tester 发现 Bug 后自动交 Debug 修复，修复后 Tester 回归，最多 3 轮。

**涉及文件**:
- `references/runner.py` — 核心改动

**关键改动**:
1. 新增 `QA_DBG_MAX_ITER = 3` 常量
2. 新增 `_tester_found_bugs(tester_result)` — 基于关键词的 Bug 检测
3. `run_project()` 执行完主 DAG 后，检查 Tester 输出：
   - 无 Bug → 直接进入 PM 整合
   - 有 Bug → 执行 mini-DAG：`[Debug] → [Tester Retest]`
   - 最多循环 3 次
   - 第 3 次仍有 Bug → 写入知识库 gotcha + escalate
4. 新增 `add_gotcha()` 调用记录反复出现的 Bug

**流程示意**:
```
[Tester] 发现Bug ──→ [Debug] 修复 ──→ [Tester] 回归
                          ↑                    │
                          └── 仍有Bug ─────────┘  (最多3轮)
                                                    │
                                          第3轮仍有 → escalate + 知识库记录
```

### 五、断点续跑（Crash Recovery）

**目标**: Server 崩溃后重启，能自动跳过已完成的 DAG 节点，从中断处继续。

**涉及文件**:
- `references/runner.py` — 快照扫描 + 跳过逻辑
- `server.py` — 启动检测恢复路径

**关键改动**:
1. `runner.py` 新增 `_find_completed_tasks_from_snapshots()` — 扫描 `state/snapshots/` 找出已完成任务
2. `run_dag()` 新增 `skip_tasks: Optional[set[str]] = None` 参数
3. 跳过逻辑：过滤掉已有快照的任务，从 `master.json` 重构结果
4. `server.py` 启动时检测 `master.json` 状态是否为 `in_progress`，若是则进入恢复模式

### 六、审批流程重设计（双阶段审批）

**目标**: 用户看到审批内容后，先确认"我正在看"（无超时），再做出决策（3600s 超时）。避免用户还没看到弹窗就被判定超时拒绝。

**涉及文件**:
- `server.py` — 全面重写 `_handle_approve()` 和 `_handle_approve_dag()`
- `references/runner.py` — 重写 `http_approval()` 和 `_request_dag_approval()`

**关键改动**:
1. **Phase 1（确认阶段）**:
   - 无超时，无限等待
   - 用户调用 `POST /approve` 携带 `{"status": "reviewing"}`
   - 服务器写入 `state/_approval_ack.json`
2. **Phase 2（决策阶段）**:
   - 3600s 超时
   - 用户调用 `POST /approve` 携带 `{"approved": true/false}`
   - 服务器写入 `state/_approval_response.json`
3. CLI 模式保持单次 `input()`（因为用户在终端前，无需两阶段）

### 九、Prompt Caching（减少 Token 费用）

**目标**: 利用 API 的 Prompt Caching 功能，对重复的 system prompt 返回缓存折扣价，减少 token 费用。

**涉及文件**:
- `references/model_adapter.py` — Claude 调用添加缓存标记

**关键改动**:
1. 新增全局开关 `ENABLE_PROMPT_CACHING = True`
2. `_call_claude()` 中：
   - 添加 `extra_headers={"anthropic-beta": "prompt-caching-2024-07-31"}`
   - system prompt 从纯文本改为：`[{"type": "text", "text": system, "cache_control": {"type": "ephemeral"}}]`
3. OpenAI/GPT-4o 的 Prompt Caching 是自动的，无需改代码
4. DeepSeek 和 Gemini 暂不支持，跳过

**预期收益**:
- 同一角色的多次调用：system prompt 100% 缓存命中 → 缓存部分仅收 50% 费用
- 以 11 角色各跑一次为例：约 1.5K×11 = 16.5K tokens 的 system prompt 可走缓存价
- 整体 token 费用可降至单 Agent 包办的 **1/3 ~ 1/2**
