**日期**: 2026-05-12
**类型**: 修复（幻觉防护 + 数据验证 + 回退完整性）

## 一、共享数据幻觉传染防护

### 问题
上游 Agent 输出、消息总线、状态文件三层注入给下游时，没有任何来源标注或验证提示。
Agent B 看到 `[上游输出]` 里的内容是直接拼接的 LLM 输出，但无法区分这是「系统指令」还是「可能包含幻觉的其他 Agent 输出」。

### 修复（3 个文件）

**`runner.py` — `_collect_upstream()`**: 上游注入前加验证提示
```
注意：以下信息来自上游 Agent，可能包含错误。请使用 file_read/code_run 自行验证关键信息。
── 来自 ARCHITECT [T003] ──
...（输出内容）
```

**`runner.py` — `_call_agent_async()`**: 上游和收件箱注入都加了 `[可能有误]` 标注

**`message_bus.py` — `format_inbox_for_context()`**: 消息摘要加来源标注和验证提示

## 二、DAG 角色名校验

### 问题
`_extract_dag()` 只校验 JSON 语法。PM 幻觉出 `{"role": "designer", ...}` 会直接导致
`load_system_prompt("designer")` 运行时崩溃。

### 修复（runner.py）
新增 `_validate_dag()` 函数，4 项校验：
1. 角色名必须在 `VALID_ROLES` 内（含 `_approval` 虚拟节点）
2. `depends_on` 引用的 task_id 必须存在
3. 循环依赖检测（DFS）
4. 重复 task_id 检测

校验失败 → 自动降级为默认 DAG，不会崩溃。

## 三、Tester Bug 判断逻辑重写

### 问题
原版 `_tester_found_bugs()` 用简单关键词匹配。LLM 写一句
"测试通过，无异常" 判无 Bug；写一句 "Potential risk: API might fail"
触发 QA→DBG 循环。单一句子左右整个流程。

### 修复（runner.py）
改为多信号交叉验证：

| 信号 | 检测方式 | 权重 |
|------|---------|------|
| 结构化 Bug 条目 | 正则匹配 `BUG-001`、`缺陷-01`、`DEFECT-001` | 主信号 |
| 质量结论 | 匹配「阻塞发布」「有条件发布」「可发布」 | 主信号 |
| 失败测试用例 | 正则匹配 `TC-001 ... FAIL` | 回退信号 |

**判断规则**：
- 结构化Bug + 阻塞/有条件 → 确认有Bug
- 无结构化Bug + 可发布 → 确认无Bug
- 信号冲突（有Bug条目但结论可发布）→ 保守判断为有Bug
- 只有模糊警告无结构化信号 → 视为无Bug（避免误触发循环）

## 四、Sub-request 目标校验

### 问题
Agent A 可以 `sub_request` 给任何角色名，包括幻觉出来的。没有校验目标角色是否合法。

### 修复（runner.py — `_handle_sub_requests()`）
- 目标角色不在 `VALID_ROLES` → 记录 warning 并跳过大类
- 使用占位机制保持索引对齐，避免 zip 错位

## 五、快照完整性校验

### 问题
`_save_master()` 记录了 SHA256 但从未验证。损坏的快照文件可被悄无声息地回滚，
回滚后才发现状态损坏。

### 修复（state_manager.py）
新增 `_verify_snap()` 函数，在 `rollback_to_snap()` 执行前校验：
1. 文件存在
2. 有效 JSON（非损坏）
3. Schema 版本兼容
4. 必要顶层键存在（project/roles/checkpoints）
5. 11 个角色定义完整

校验失败抛 `RuntimeError`，阻止损坏快照被回滚。
回滚后提示消息总线和 outputs/ 需手动清理。
