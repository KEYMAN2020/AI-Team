# 数据治理与合规约束草案（DB）

项目：n8n_0523_2114  
版本：v0.1（初始化阶段）  
角色：DBA  

---

## 1. 目标与适用范围

本文档用于约束数据库层面的数据治理与合规实践，重点覆盖：

1. 实名数据最小化
2. PII（个人身份信息）字段加密
3. 审计留痕与可追溯性

适用对象：BE（ORM 与访问控制实现）、OPS（部署与密钥管理）、DBA（Schema/Migration/权限审计）。

---

## 2. 实名数据最小化（Data Minimization）

### 2.1 基本原则

- **目的限定**：仅采集业务功能必需字段，禁止“先采后用”。
- **最小够用**：能用标识符（如 user_id）替代实名信息时，不落库实名字段。
- **分层存储**：实名信息与业务行为数据分表/分域存储，降低横向暴露面。
- **默认非必填**：除法律合规或核心流程强制要求，实名字段应 `NULLABLE`。
- **生命周期控制**：设置保留期，到期自动脱敏/删除。

### 2.2 字段采集建议（草案）

- 姓名：仅在实名认证流程采集；非认证场景不得采集。
- 身份证号/护照号：原则上不存明文，优先“校验即弃”；确需留存时只保存：
  - 加密密文（可逆，受严格权限）
  - 不可逆哈希（用于去重/检索）
- 手机号/邮箱：仅用于登录、通知、风控，禁止用于无关画像。
- 出生日期、住址：非业务强依赖不采集；采集时优先粒度降级（如年龄段、省份）。

### 2.3 数据保留与删除

- 实名认证原始材料（如证件号密文）应设置最短合法保留期。
- 注销用户触发“删除/匿名化流水线”：
  - 业务主键保留（用于账务与审计一致性）
  - 直接身份标识删除或不可逆匿名化
- 删除动作必须落审计日志（见第4章）。

## 3. PII 字段加密建议

### 3.1 字段分级

建议按敏感等级分级：

- **S3（高敏）**：身份证号、护照号、银行卡号、人脸模板
- **S2（中敏）**：手机号、邮箱、详细住址
- **S1（低敏）**：姓名（单独存在时）、公司、职位

### 3.2 加密与脱敏策略矩阵

| 数据类型 | 存储策略 | 检索策略 | 展示策略 |
|---|---|---|---|
| 证件号（S3） | 强制加密（AES-256-GCM/等效）+ 独立哈希列 | 通过哈希精确匹配，不对密文做 LIKE | 默认仅展示后4位 |
| 手机号（S2） | 建议加密 + 哈希列 | 哈希等值查询；必要时维护脱敏索引字段 | `138****1234` |
| 邮箱（S2） | 建议加密 + 规范化哈希（小写/trim） | 哈希等值查询 | `a***@xx.com` |
| 姓名（S1） | 视业务可明文或加密 | 若用于检索，优先额外拼音/分词索引（非明文暴露） | 部分掩码 |

### 3.3 密钥管理要求

- 密钥不得入库、不得写死在代码仓库。
- 使用 KMS/HSM 托管主密钥，应用侧仅持有短期数据密钥。
- 轮换策略：
  - 主密钥至少年度轮换
  - 高敏字段支持“重加密迁移”
- 环境隔离：dev/test/prod 密钥严格分离。

### 3.4 实施细则（DB/ORM 协同）

- 数据库仅存：`ciphertext`、`hash`、`mask`（可选）三类字段。
- `hash` 使用带业务域分隔的 HMAC-SHA256（避免跨系统撞库关联）。
- 禁止在 SQL 日志、慢查询日志中输出明文参数（开启参数脱敏）。
- 仅授权服务账号可解密；人工 DBA 默认不可直接解密。

## 4. 审计留痕策略（Auditability）

### 4.1 必审计事件

以下操作必须留痕（不可关闭）：

1. PII 查询（特别是批量导出）
2. PII 新增/修改/删除
3. 解密调用
4. 权限变更（角色、策略、密钥权限）
5. 数据导出、备份下载、跨境传输

### 4.2 审计日志字段规范

建议统一审计表/审计流字段：

- `event_id`：全局唯一ID
- `event_time`：事件时间（UTC）
- `actor_type`：human/service/system
- `actor_id`：操作者标识
- `role_snapshot`：操作时角色快照
- `action`：READ/UPDATE/DELETE/DECRYPT/EXPORT...
- `resource_type`：table/row/api/report
- `resource_id`：资源标识
- `pii_scope`：涉及PII类别（S1/S2/S3）
- `purpose_code`：访问目的（客服、风控、合规核查等）
- `result`：SUCCESS/FAIL
- `client_ip`/`trace_id`：链路追踪
- `before_hash`/`after_hash`：变更摘要（避免写入明文）

### 4.3 留存与防篡改

- 审计日志至少保留 180 天（按监管要求可延长至 1~3 年）。
- 审计数据写入后不可更新，仅允许追加。
- 使用 WORM（Write Once Read Many）或对象存储版本锁定策略。
- 建立异地备份与定期校验（哈希完整性校验）。

### 4.4 告警与审计巡检

- 实时告警场景：
  - 单账号高频查询 S2/S3
  - 非办公时段批量导出
  - 非授权服务调用解密接口
- 每月执行一次权限回顾（Access Review）与异常访问复盘。

## 5. 数据库权限与访问分级

- **最小权限原则（PoLP）**：
  - 应用账号按服务拆分，不共享超级账号。
  - 读写分离账号，PII 表单独授权。
- **分级访问**：
  - L1：非敏数据读写
  - L2：S2 数据受控访问
  - L3：S3 数据与解密权限（双人审批）
- 生产库禁止直连写操作；紧急变更走工单与审计。

---

## 6. 与后续 Schema/Migration 对接建议

后续建表建议默认带以下字段与约束：

- 业务表：`created_at`, `updated_at`, `deleted_at`（软删可选）
- 敏感字段：`xxx_ciphertext`, `xxx_hash`, `xxx_mask`
- 索引：对 `xxx_hash` 建唯一或普通索引（按业务）
- 审计表：按时间分区（大体量场景）+ `actor_id/event_time/action` 复合索引

## 8. 风险提示

- 仅加密不做权限收敛，无法满足合规“最小可见”要求。
- 仅做应用层审计而无数据库侧审计，难以覆盖越权直连风险。
- 哈希策略若无“域隔离（pepper/salt/HMAC key）”，存在跨库关联风险。
